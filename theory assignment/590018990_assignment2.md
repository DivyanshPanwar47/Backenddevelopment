## Part A - Conceptual questions

### 1. What is `jsonb` in PostgreSQL, and how does it differ from plain `json`?

PostgreSQL's `jsonb` is a binary, decomposed representation of JSON. PostgreSQL parses the document when it is written and stores its structure rather than retaining the original text. The plain `json` type stores the input as text, so it preserves whitespace and the order of object keys. Both types validate that the value is valid JSON, but `jsonb` is normally the better choice when an application will query the document or index its fields. The parsing and conversion work makes `jsonb` writes slightly more expensive than plain `json` writes. In return, PostgreSQL can inspect `jsonb` values efficiently and can build GIN indexes over their keys and values. Repeated searches therefore tend to be much faster with `jsonb`, especially for containment and key-existence predicates. `jsonb` does not preserve duplicate object keys or formatting, so it is not appropriate when the original JSON text must be reproduced exactly. For most application data, the query and indexing advantages outweigh the small write cost.

```sql
CREATE TABLE events (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload JSONB NOT NULL
);

INSERT INTO events (payload)
VALUES ('{"type":"login", "user_id": 42}'::jsonb);

SELECT payload->>'type' AS event_type
FROM events
WHERE payload @> '{"user_id": 42}';
```

### 2. How can PostgreSQL work as both a SQL and a NoSQL database in the same table?

A PostgreSQL table can keep important, frequently queried fields as strict relational columns while placing variable or category-specific properties in one `jsonb` column. The typed columns provide primary keys, `NOT NULL` rules, numeric types, foreign keys and reliable joins. The JSONB column behaves like a document attached to each row: one product can have `pages` and `author`, while another can have `ram_gb` and `cpu`, without adding a new table column for every possible property. This is a hybrid design rather than an entirely schema-free design. The application can enforce the common structure with SQL constraints and validate the flexible part at the service boundary. PostgreSQL can then combine normal SQL predicates with JSONB operators in one query. This is useful when the stable identity and commercial fields need reporting, but optional attributes change by category or evolve quickly. If a flexible attribute becomes important for reporting, it can later be promoted to a typed column or exposed through an expression index.

```sql
CREATE TABLE products (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price NUMERIC(10, 2) NOT NULL CHECK (price >= 0),
    attributes JSONB NOT NULL DEFAULT '{}'::jsonb
);

SELECT name, price, attributes->>'material' AS material
FROM products
WHERE attributes @> '{"material": "steel"}';
```

### 3. Give an example of `->`, `->>`, `@>` and `?`, with the value returned.

The `->` operator extracts a JSON value and keeps it as JSON. The `->>` operator extracts a field and converts the result to PostgreSQL text. That distinction matters when the extracted value will be cast to an integer, compared as text, or returned to an API. The `@>` operator tests whether the left JSONB document contains the right JSONB structure. The `?` operator tests whether a top-level key or array string exists. Assume the row below has the shown `attributes` value. `attributes -> 'pages'` returns the JSON number `464`, while `attributes ->> 'pages'` returns the text value `'464'`. The containment query returns `true` because the document contains the requested key/value pair. The key-existence query returns `true` because `author` is a top-level key. These operators can be combined with ordinary SQL conditions such as `category`, joins or ordering.

The result type also affects application code: JSON output can be traversed with more JSON operators, while text output can be passed directly to a display layer or cast to a native SQL type. If a requested key does not exist, both extraction operators return `NULL`, which is useful for optional attributes but should be considered when writing filters.

```sql
-- attributes = {"author":"Robert C. Martin", "pages":464, "format":"paperback"}
SELECT attributes -> 'pages' AS json_value;
-- returns: 464

SELECT attributes ->> 'pages' AS text_value;
-- returns: '464'

SELECT attributes @> '{"format":"paperback"}' AS contains_pair;
-- returns: true

SELECT attributes ? 'author' AS has_author;
-- returns: true
```

### 4. How can a GIN index on a `jsonb` column change query performance?

A GIN index stores an inverted mapping from JSON keys and values to the rows containing them. With the default `jsonb_ops` operator class, it can accelerate predicates such as containment (`@>`) and top-level key checks (`?`, `?|` and `?&`). Instead of scanning every JSON document, PostgreSQL can identify candidate rows from the index and then recheck the JSON condition. The improvement is most visible on a large table with selective predicates; on a five-row classroom dataset, the planner may correctly choose a sequential scan because reading the whole table is cheaper than using an index. A normal GIN index on the column does not automatically speed up every expression involving extracted text. For example, comparing a casted value with `(attributes->>'ram_gb')::int >= 16` may require an expression index if that comparison must be fast. GIN indexes also add storage and make writes more expensive, so they should be added when the workload contains enough JSONB reads to justify them.

```sql
CREATE INDEX idx_products_attributes_gin
ON products USING GIN (attributes);

SELECT name
FROM products
WHERE attributes @> '{"wireless": true}';
```

### 5. Where could PostgreSQL + `jsonb` replace MongoDB, and where would MongoDB still be the better fit?

PostgreSQL plus `jsonb` can replace MongoDB when the application needs strong transactions, joins, reporting, foreign keys or a stable relational core with a moderate amount of flexible data. One transaction can update typed columns and JSONB attributes together, and SQL can join products to orders, users and suppliers without duplicating data. PostgreSQL also supports schema enforcement for the important fields while leaving optional attributes flexible. MongoDB is often a better fit when documents are naturally self-contained, their shapes vary substantially, and the system needs document-oriented development with very high horizontal scale across distributed nodes. MongoDB's sharding model and document locality can be attractive for workloads that rarely join data and that grow across many machines or regions. PostgreSQL can scale out through extensions and replicas, but a distributed MongoDB deployment may be simpler for a document-first workload. The choice should therefore follow access patterns: use PostgreSQL when consistency, joins and mixed SQL/JSON queries dominate; choose MongoDB when independent aggregate documents, rapid schema variation and horizontal distribution dominate.

```sql
BEGIN;
UPDATE products
SET price = price * 0.95,
    attributes = attributes || '{"sale": true}'::jsonb
WHERE id = 1;
COMMIT;
```

### Task 3 - Query by category-specific attribute

These queries filter through JSONB attributes rather than filtering by product name, category or price.

```sql
-- Books with more than 400 pages.
SELECT name, attributes ->> 'author' AS author, (attributes ->> 'pages')::int AS pages
FROM products
WHERE (attributes ->> 'pages')::int > 400;
```

```sql
-- Laptops with at least 16 GB RAM.
SELECT name, attributes ->> 'cpu' AS cpu, (attributes ->> 'ram_gb')::int AS ram_gb
FROM products
WHERE (attributes ->> 'ram_gb')::int >= 16;
```

```sql
-- Products that support wireless connectivity.
SELECT name, attributes ->> 'connection' AS connection
FROM products
WHERE (attributes ->> 'wireless')::boolean = true;
```

### Task 4 - Containment query

```sql
SELECT name
```

### Task 5 - Update JSONB without altering the table

The concatenation operator `||` adds or replaces keys in the JSONB object without changing the table schema.

```sql
UPDATE products
SET attributes = attributes || '{"discount_pct": 10}'::jsonb
WHERE name = 'Wireless Mouse'
RETURNING name, attributes;
```

Expected JSONB attributes after the update:

```json
{
  "color": "midnight",
  "wireless": true,
  "connection": "Bluetooth",
  "discount_pct": 10
}
```

### Task 6 - Index and compare

Run the category-specific queries from Task 3 before creating the index, then create the index and run them again.

```sql
EXPLAIN ANALYZE
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}'::jsonb;

CREATE INDEX idx_products_attributes
ON products USING GIN (attributes);

EXPLAIN ANALYZE
SELECT name
FROM products
WHERE attributes @> '{"wireless": true}'::jsonb;
```

The GIN index is designed for containment and key-existence operators. It may be used for the `@>` query once the table is large enough and the predicate is selective. With only five rows, PostgreSQL may continue to show a sequential scan because that is cheaper; this is an expected cost-based decision, not evidence that the index is invalid. The Task 3 numeric comparisons extract text and cast it to an integer, so the general GIN index is not guaranteed to help them. If those comparisons become a hotspot, an expression index is more appropriate:

```sql
CREATE INDEX idx_products_ram_gb
ON products (((attributes ->> 'ram_gb')::int));
```

Equivalent category-specific queries:

```javascript
// Books with more than 400 pages.
db.products.find(
  { assignment: 'assignment2', 'attributes.pages': { $gt: 400 } },
  { _id: 0, name: 1, 'attributes.author': 1, 'attributes.pages': 1 }
);

// Laptops with at least 16 GB RAM.
db.products.find(
  { assignment: 'assignment2', 'attributes.ram_gb': { $gte: 16 } },
  { _id: 0, name: 1, 'attributes.cpu': 1, 'attributes.ram_gb': 1 }
);

// Products with wireless support.
db.products.find(
  { assignment: 'assignment2', 'attributes.wireless': true },
  { _id: 0, name: 1, 'attributes.connection': 1 }
);

// Containment-style query.
db.products.find({ assignment: 'assignment2', 'attributes.wireless': true });

// Add a JSON-style field without altering a table schema.
db.products.updateOne(
  { assignment: 'assignment2', name: 'Wireless Mouse' },
  { $set: { 'attributes.discount_pct': 10 } }
);
```

Index and performance comparison:

```javascript
db.products.createIndex({ 'attributes.wireless': 1 });
db.products.find({ assignment: 'assignment2', 'attributes.wireless': true }).explain('executionStats');
```

PostgreSQL uses SQL expressions and operators such as `->>`, `@>` and `?`, while MongoDB uses a document query object with dotted paths and operators such as `$gte` and `$set`. MongoDB's nested-document syntax is concise for document-shaped reads and its schema flexibility is natural. PostgreSQL provides stronger relational constraints, joins, transactions and one SQL language for typed and JSONB fields. For a small catalog both are easy to use; the better choice depends on whether relational integrity and cross-table reporting or independent document distribution is more important.
